# Production Deployment

This project is prepared for a two-service Render deployment:

- student-dashboard-api — Node.js + Express web service backed by MongoDB.
- student-dashboard-web — React + Vite static site served through Render's CDN.

The repository contains a root render.yaml Blueprint so the deployment topology is version-controlled.

## 1. Prerequisites

You need:
- A Render account connected to the GitHub repository.
- A production MongoDB deployment, such as MongoDB Atlas.
- A production database user and connection string.
- The repository's main branch available to Render.

Do not commit production secrets to Git.

## 2. Create the Render Blueprint

In Render:
1. Create a new Blueprint and select this repository.
2. Select the main branch.
3. Render reads the root render.yaml and creates the API and frontend services.
4. When prompted for sync: false values, provide the production values described below.

Render's Blueprint format supports separate web and static services, per-service root directories, build commands, environment variables, and HTTP health checks. The Vite frontend is built to dist, while the API exposes /health/ready for readiness checks. [Render Blueprint Reference](https://render.com/docs/blueprint-spec)

## 3. Configure API environment variables

For student-dashboard-api:

| Variable | Value |
|---|---|
| NODE_ENV | production |
| MONGO_URI | Your production MongoDB connection string |
| JWT_SECRET | Generated by Render |
| CLIENT_ORIGIN | Exact HTTPS URL of the frontend |
| TRUST_PROXY | true |
| COOKIE_SECURE | true |
| COOKIE_SAMESITE | lax |
| ACCESS_TOKEN_TTL_SECONDS | 900 (15 minutes) |
| REFRESH_TOKEN_TTL_SECONDS | 604800 (7 days) |
| REDIS_REST_URL | Upstash Redis REST endpoint |
| REDIS_REST_TOKEN | Upstash Redis server-side token |

The Blueprint generates JWT_SECRET rather than storing it in Git. The production cookie must be secure because the deployed application uses HTTPS.

For distributed login rate limiting, create a production Redis database (Upstash Redis REST is the documented setup) and supply its HTTPS endpoint and server-side token. Keep the token only in the API service environment; never add it to the frontend or repository.

TRUST_PROXY=true is intentional for the Render reverse-proxy deployment. Keep it enabled only when the service is actually deployed behind the trusted proxy topology described by the application configuration.

## 4. Configure the frontend

For student-dashboard-web, set VITE_API_BASE_URL to the deployed API URL, for example:

    VITE_API_BASE_URL=https://<your-api-service>.onrender.com

Vite environment variables are injected at build time for a static site. If the API URL changes, update this variable and redeploy the frontend. [Render static-site deployment guidance](https://render.com/tutorials/web-service-vs-static-site/static-sites)

After the frontend receives its Render URL, update the API's CLIENT_ORIGIN to that exact URL and redeploy the API if necessary.

## 5. MongoDB

Use a production MongoDB instance rather than the local development database.

Create a dedicated database user with only the permissions the application needs. Configure MongoDB network access according to your hosting/network policy and avoid committing the connection string.

The API does not expose the MongoDB connection string through its HTTP responses.

## 6. Verify the deployment

API liveness:

    GET https://<your-api-service>.onrender.com/health

Expected: {"status":"ok"}

API readiness:

    GET https://<your-api-service>.onrender.com/health/ready

Expected when MongoDB and Redis are reachable:

    {"status":"ready","database":"connected","rateLimitStore":"connected"}

A 503 from /health/ready means the API process is running but MongoDB or the production rate-limit store is not ready.

Frontend verification:
1. Open the frontend Render URL.
2. Verify student login.
3. Verify faculty login.
4. Verify dashboard data, attendance, marks, and timetable requests.
5. Verify faculty write operations.
6. Verify logout and subsequent login.
7. Confirm browser requests reach the API without CORS or CSRF errors.

Render HTTP health checks use the configured path to decide whether a web service is ready to receive traffic. [Render health checks](https://render.com/docs/health-checks)

## 7. Production deployment checklist

- [ ] NODE_ENV=production
- [ ] JWT_SECRET is generated/stored by Render
- [ ] MONGO_URI is a production database
- [ ] REDIS_REST_URL points to the production Redis REST endpoint
- [ ] REDIS_REST_TOKEN is stored only in the API environment
- [ ] COOKIE_SECURE=true
- [ ] CLIENT_ORIGIN is the exact frontend origin
- [ ] Frontend VITE_API_BASE_URL points to the deployed API
- [ ] API /health returns 200
- [ ] API /health/ready returns 200
- [ ] Frontend loads successfully
- [ ] Login/logout works
- [ ] Access tokens are short-lived and refresh sessions rotate
- [ ] Refresh-token replay is rejected
- [ ] Browser cookies are Secure/HttpOnly as intended
- [ ] No production secrets are committed
- [ ] Latest GitHub Actions run is green before deployment

## Render operational note

Render web services must listen on the assigned PORT and be reachable on 0.0.0.0. The API now explicitly follows that contract and performs graceful HTTP/MongoDB shutdown on termination signals. [Render web services](https://render.com/docs/web-services)

The frontend is a static Vite site, so its API URL is baked into the production bundle at build time. [Render static sites](https://render.com/docs/static-sites)
